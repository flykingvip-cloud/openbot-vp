## 2. 核验证据

### 2.1 P0-1 — `loom task land` 不是 Landing Queue（成立，且比专家描述更严重）

| 断言                                     | 核验结果                                                                                                                                                                                |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 锁按 `taskId` 创建，不同 task 可并行落地 | **成立**。`scripts/loom/provision.ts:490` 锁路径为 `.loom/.locks/${lockNameOf(taskId)}.lock`（`lockNameOf` 在 `:468`）。这是**互斥重复落地同一 task**的锁，不是串行化落地本身的全局锁。 |
| 无队首、无全局锁、无失败退尾、无队列状态 | **成立**。`land()`（`:617`）是单次落地流程，无任何队列结构。                                                                                                                            |
| CLI 未注入 `runGate`，门禁默认直接通过   | **成立**。`scripts/loom.ts:554` 传入的 io 仅 `{ git, loadRegistry, saveRegistry }`；`provision.ts:650` 回退为 `io.runGate ?? (() => true)`。**即 CLI 落地路径不跑任何门禁。**           |
| fetch 失败后继续基于本地 base 操作       | **成立**，且后果被低估 —— 见新增缺陷 B。                                                                                                                                                |

**新增缺陷 A（专家未提及）**：同一处 io 也未注入 `prCreate`。`provision.ts:680` 为 `io.prCreate?.(branch, worktreePath)` —— 可选调用。因此 `loom task land --mode pr` 会 `git push` 分支、把 task 置为 `landed`、删除 worktree，然后**静默地不开任何 PR**。而 `defaultLandMode` 默认就是 `"pr"`（`provision.ts:51`）。这比"门禁不生效"更糟：它会产出"已落地"的 registry 状态，而 main 上什么都没进。

**新增缺陷 B（专家未提及）**：`provision.ts:632` 的 `base = config.defaultBase` 是 `"main"` —— **本地** main ref，不是 `origin/main`。实测本地 `main` = `d2812eea9e`，`origin/main` = `d844a6792e`，**本地落后 15 个 commit**。fetch 失败被 `catch {}` 吞掉后，rebase 落在过期 base 上；后续 `mergeFfOnly` 要么失败、要么产出错误结果。

**结论**：requirements R8.3（队列语义）与 R8.4（"SHALL NOT 新建调度器，能力已存在"）确实互相矛盾。D1-C 不是"已建好只需接线"，而是**一项新的高风险协调能力**。这是本次审核最重要的纠正 —— 我在材料中把"手工版串行队列"读成了"队列能力已存在"，而实际连门禁与开 PR 都没接上。

### 2.2 P0-2 — `loom check --strict` 不是归因/结构门禁（成立）

`scripts/loom/check.ts` **完全不引用 `lintRegistry`**（grep 无命中）。`runCheck` 只做 legacy↔registry 的归因/审计 parity 比对。

实测：

| 命令                  | 结果                                                  |
| --------------------- | ----------------------------------------------------- |
| `loom check --strict` | **exit 0**                                            |
| `loom lint`           | **123 条**，其中 **18 条 error**（`impossible-glob`） |

专家给出的 123 与实测**完全一致**。

**结论**：requirements R6.4、design §8、tasks 2.4 把"移除 `ci.yml:237` 的 `continue-on-error`"等同于"`ownership-overlap` 成为真实门禁"**不成立**。必须单独把 `loom lint` 接入 CI，或显式扩展 `loom check` 的契约。

### 2.3 P0-3 — backup 分支无法备份脏文件（成立）

`backup/<topic>-<YYYYMMDD>` 只保存提交图。当前约 **209 个已修改/未跟踪文件**（其中 **141 个 UNATTRIBUTED**）不在任何提交里，建 ref 对它们**零保护**。

我在材料 D4 里把 2026-07-27 事故后确立的协议直接套用过来 —— 但那次事故保护的对象是**已提交但被 force-push 丢弃的 40 个 commit**，与"未提交的工作树内容"是两类完全不同的东西。这是一处**类比失当**，接受批评。

### 2.4 P1-4 — Blacksmith Option A 仍保留假基础设施（成立）

仅加注释而让 job 继续挂在默认触发路径上，依然产生 queued/cancelled 噪声 —— 这恰好违反我自己在 R7 写的"不存在的基础设施不参与治理"。**自相矛盾，接受**。

### 2.5 P1-5 — ruleset 无法证明 Landing Queue 是唯一入口（成立）

required checks 只能证明某 SHA 通过了检查，无法证明它**经由** Loom 队列产生。`allow_auto_merge` 是"条件满足后自动合并"，不是队列。materials R8.5 称 ruleset 为"服务端保底、使绕过队列的落地在服务端失败"——**表述过强**，应改为"防止直推"而非"证明入口唯一"。

### 2.6 P1-6 — 「每条 SHALL 都有机器拒绝」尚未兑现（成立）

design §8 映射表中仍大量标注"待新增 / 待开启 / 部分"。且两类落点根本不是拒绝器：

- `AGENTS.md` 是**行为规范**，不是机器；agent 可以不读、读了可以不遵守
- PR 模板**无法强制填写**

R14 应拆成三类，不能一律称"机器落点"：

| 类别               | 含义             | 例                                                       |
| ------------------ | ---------------- | -------------------------------------------------------- |
| **强制门禁**       | 违反则动作被拒   | ruleset、required checks、`lint` 的 error 级别 + CI 接入 |
| **自动检测不阻断** | 机器会报，但不拒 | `loom lint` 的 warn、shadow 结构 lint                    |
| **人工流程约束**   | 靠人遵守         | `AGENTS.md` 条款、PR 模板字段                            |

这是对 R14 的实质修正 —— 我把"有落点"和"会拒绝"混为一谈了。

## 7. 本次审核暴露的方法论问题（自查）

三处 P0 有一个共同根因：**我把"资产存在"读成了"能力可用"**。

- `loom task land` 有落地代码 → 我称"队列能力已存在"，但没验证 CLI 是否接上门禁与开 PR
- `loom check --strict` 在 CI 里且 exit 0 → 我称它是归因门禁，但没验证它到底检查什么
- backup 分支是事故后确立的协议 → 我直接套用，没区分"已提交 commit"与"未提交工作树"

这与我在材料 §0 批评仓库的问题**是同一种错误**：假门禁的成本不是它不工作，而是它让人以为有保护。我在诊断别人的假门禁时，自己写了三条假保护。

**纠正措施**：后续凡声称某能力"已存在"，必须给出该能力**被实际调用**的证据（调用点行号 + 实测输出），而非仅给出实现存在的证据。此条建议加入 `AGENTS.md` 的 bug-fix 合并门槛（当前只要求"验证根因"，未要求"验证调用链接通"）。
