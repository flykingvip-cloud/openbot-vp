# Runtime convergence migration contract

## Target

Command owns message interpretation and accepted task amendments. Execution retains the existing runner and bounded continuation. Delivery owns acceptance presentation and transport receipts. Context supplies ordered, trust-labelled model input; capabilities supply authorized actions. State owns atomic task mutations. Policy returns decisions, not side effects. Wiring injects dependencies, not business decisions.

These are responsibilities, not permission to create parallel engines. Session task records, shared collaboration contracts and private executor plans remain distinct until their scope and consumer evidence justify a change.

## Migration checkpoints

- M0: authority and extension disposition maps with source evidence and explicit unknowns.
- M1: equivalent context material assembly extraction; source builders remain in original order and execute exactly once.
- M2: capability contract and invocation boundary; preserve permission, hook and abort wrapper order.
- M3: command/execution/delivery boundaries; retire the displaced decision path in the same coherent change.
- M4: separately evidenced lifecycle gaps; no speculative engine.
- M5: retire redundant executable configuration and alternate controls only with consumers, replacement and recovery evidence.

## M1 acceptance

No schema, authorization, budgeting values, model calls, scheduling or continuation changes. Preserve exact prompt strings, ordering, duplicates, whitespace filtering semantics and system versus untrusted-user placement. No configured modules/scripts/callbacks are introduced. Pure assembly may accept an existing source-code formatting dependency; this is not an executable configuration surface.

Use existing architecture manifest rules, scoped runtime tests and baseline/candidate diagnostics. Build module changes and identify dynamic-import warning deltas. A successful build alone does not waive new warnings. Owner integrates and commits; contributors do not land.

## M1 concrete boundary

Initial API exposes ordered system-material selection, append and finalization. Inputs are source-code-created text values, never executable loaders or configuration callbacks. Migration points: get-reply-run collaboration and normal initial arrays, later source append operations, and final system prompt join. Untrusted user-body formatting stays on the original path for the first checkpoint. Original source builder calls stay in their current order and execute once. No new de-duplication or whitespace normalization.

An architecture manifest rule explicitly prohibits context assembly imports of gateway, agents, conversation-task, auto-reply, plugins and cron. Root AGENTS applies; the new directory has no overriding instructions.
