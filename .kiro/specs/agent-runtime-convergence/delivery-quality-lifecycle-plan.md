## 目标与结构

交付层从“回复整理与发送”扩展为：成果质量验收、成果呈现、受治理的保存与版本、投递回执、审核沉淀与复用。保留业务三层、两类供给、公共机制，不新建质量执行器、成果库或第二状态机。

```text
指挥层：确定成果类型 / 内容要求 / 来源范围 / 时效 / 视觉偏好 / 验收项
   ↓ 选定有版本的质量规则，不在执行后反推必测项
执行层：原 runner + 原能力调用 → 生成原件和来源证据
   ↓
交付层：原件定位与版本确认 → 质量检查与原验收回执 → 成果呈现/投递
   │                            │ 未通过：返回原执行/修复机制
   │                            └ 无法检查：明确未检查，不能自动通过
   └ 同一成果版本的操作视图：预览 / 下载 / 保存 / 二次编辑 / 知识库归档 / 审核复用

公共机制：身份权限、规则选择、合法状态转移、预算、审计
共享供给：任务/对话/记忆/知识和 Skill 指导；外源材料保持不可信数据边界
```

排版指导在生成之前供给模型，质量检查在实际原件产生之后执行。检查失败回到既有 execution verification/recovery；检查本身不获得独立调度、重试、写看板或终结任务的权限。

## 质量规则体系

规则按成果类型、任务风险、用途和用户偏好选择。规则是有版本的标签、分类矩阵、阈值和引用，不是可执行配置；validator是经过注册、受能力权限约束的固定代码组件。禁止在配置里注入shell、JS、任意模块路径、表达式执行或隐藏重试脚本。

| 维度         | 可检验标准与证据                                                                                                   | 判定限制                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 输出规范     | 用户要求、必需章节/字段、成果类型、语言、单位/日期、结论与附件、引用格式；对应schema和规则版本                     | 普通聊天不强制走重文件质检；不同成果不强制同一模板                          |
| 数据与来源   | 获取方式/时间、原文或受权限保护的快照、位置/页码/时间戳、关键claim到source映射、数据时间口径、计算可复算、冲突披露 | 可追溯不等于真实；链接能打开不等于支持结论；未知/矛盾必须保留，禁止补造引文 |
| 文件完整性   | 原件存在、非空、类型可解析、实际MIME/结构、公式/链接/附件、完整原件hash                                            | 文件存在或模型说“已完成”不是验收通过                                        |
| 排版与可读性 | 对实际交付版本做原格式渲染；页图/截图、缺字、裁切、遮挡、图表标签、最小字号、对比、打印页和屏幕适配                | 抽取文字或HTML替代预览不能证明原文件无排版问题；无renderer须标未检查        |
| 审美         | 版本化模板/设计tokens：层级、对齐、留白、密度、色彩、图表表达、品牌和用户偏好；模型视觉评审或人工反馈须注明方法    | 主观审美与事实/格式分列；不靠单一总分掩盖硬性失败，不把模型自评当真实性证明 |
| 使用体验     | 成果可打开、原件可下载；支持的编辑可写回；失败可解释且可恢复；权限与动作一致；操作回执真实                         | 预览失败与原件不可用分开；文件保存、KB归档、索引可用不能用一个saved状态混称 |

检查项状态至少可投影为 passed / failed / not_checked / not_applicable；先适配原ValidationReceipt/ValidatorMatch，不另建平行验收账本。必需检查未通过或未执行时，不能自动acceptanceVerified。草稿/降级交付仅在原任务合同允许时展示，明确未完成项；不得把草稿标成正式通过。

来源真实性按“证据可追溯、与断言相关、内容支持、时间口径一致”逐项报告，不承诺一个万能的真实性布尔值。合法引用的外源内容不会因此获得指令权限；质量检查不得绕过既有上下文信任或访问控制。

## 同一成果版本的贯通契约

先建立现有身份的适配映射，再收敛公开契约；不批量换ID，不复制新的成果权威存储。

- 逻辑关系：任务/attempt或协作scope → logicalId → 正式deliverableId → 具体原件版本/rawHash。
- 展示关系：UI artifactId、预览URL、下载URL是正式成果版本的视图/别名；正式ID尚未产生时保持临时身份，不假装已归档。
- 存储关系：受授权的出生工作区定位、正式文件、KB documentId/archive记录保留各自含义并显式关联；路径和标题不是唯一身份。
- 哈希含义：正文规范化hash可用于UI去重；原件字节hash用于版本、保存冲突和验证回执；语义预览、截图和索引是派生物，记录它们对应的原件版本，不能互当字节相等。
- 质量报告：绑定task/scope、正式/临时成果映射、原件hash、规则/validator版本及来源证据版本；编辑后只可复用确实仍适用的检查，其余标过期/重新验证，禁止旧绿灯覆盖新版本。
- 操作命令：预览/编辑/保存/归档都针对显式版本；现有写API渐进补expected原文hash/版本，在原临界区比较后写入，防止检查与写入间的覆盖窗。
- 操作回执：分别确认原件保存、知识库原文归档、索引完成/可检索、外发投递；失败不撤销已完成的事实，不提前清dirty，不假报整体成功。
- 审核复用：保留原有自动capture规则，但capture/归档不自动等于知识事实已验证或可复用发布。沿既有治理流程和用户授权处理审核、转发/分享、沉淀和撤回。

用户体验：聊天给结论及成果入口；预览窗展示当前版本、草稿/已保存/归档状态和必要质量限制；不同入口指向相同原件版本。修订后的内容与旧KB归档不同步时必须可见，不能让用户误以为两者都是最新。

## 实施顺序和验收门禁

### DQ0 既有契约映射与分类矩阵

先核实 validator 必需项来自任务合同而非已有receipt列表，并追踪实际检查调用；建立上述ID/hash/状态与原schema逐项映射。选择报告和PPTX两种现有类型，不发布新的通用平台。

交付：字段责任表、质量profile及必需/建议矩阵、原调用链证据、原数据兼容方案。只有已追踪的入口可标为完成。

### DQ1 一个成果走完纵向闭环

首选已有PPTX编辑链：生成原件→聊天/预览→修改slide→保存出生工作区→刷新/重新打开→原saveAndArchive→KB原件/预览→再次编辑与冲突/另存为。核对相同成果关联、原件hash、slide内容、回执和权限。个人机器人与协作组各验证原适配器，不合并两类任务生命周期。

先写旧版本覆盖和“旧预览保存覆盖新原件”的失败反例，再在原patch/save入口修复；要求比较与写入处在原锁/原子更新边界。禁止另开写口或只在UI检查版本。

### DQ2 来源与内容验收

在同一条报告成果链补关键claim→原文位置、时效、数据口径、复算与冲突。接原validator和验收回执。红例：缺来源、链接可访问但不支持结论、数字口径不一、引用/原文版本已变。来源失效不伪造通过。

### DQ3 排版与审美

依成果类型复用既有受控渲染能力，分别验证真实PPTX/Word/PDF而非只验抽取HTML。记录具体页码/对象的溢出和可读性问题，再补审美rubric及用户偏好；修复仍回原执行主线并重验新hash。红例：文字遮挡、截断、缺字体、图表单位缺失，及“没有渲染器却报告通过”。

### DQ4 跨入口回归与受治理复用

覆盖预览/下载/保存/编辑/归档/刷新恢复；文本/HTML与Office/二进制；个人/协作；无权访问；双客户端并发；重复请求；归档/索引部分失败；用户暂停/取消及迟到回包。按真实回执展示状态；经原治理审核后才进入相应复用路径。

现有“允许静默被记为已交付”的独立问题继续保留跟踪，不以新增质量体系掩盖。Builder规范与复测、用户动作折叠时间线的原有后续任务也保留。
