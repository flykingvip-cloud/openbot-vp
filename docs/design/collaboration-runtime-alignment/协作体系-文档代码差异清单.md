旧文作为体系方向仍然有效。下面只改那些已经与 main 不符、或把目标态写成了现状的句子。

## 1. 必须删掉的说法

- 旧文 G1 写「Floor 方案：全仓无 Episode/Beat/FloorBid」。这句话作废。main 已有 `episode-state.ts`、`episode-state-machine.ts`、`episode-store.ts`、`floor-bid.ts`、`router-l0.ts`、`router-l1.ts`、`floor-shadow.ts`、`runtime-authority.ts`。
- 不得把「有 beatId / 有 `BEAT_ACTIVE`」写成「Beat Controller 已上线」。`BeatExecutionInput` 是 `executeCollaborationRound` 的参数类型。
- 不得把 Facilitator `CHALLENGE`、`REQUEST_EVIDENCE` 写成已落地机制。`src/gateway/collaboration-dispatch` 中没有这两个动作名。
- 不得把 namespace、Handoff、Episode Store、EDR/PDR 写成生产主路径。它们的旗标默认关闭。

## 2. 旧文主张与 main 的差异

- 旧文 §3.5 把 Floor 写成工程方案中的 P3+，并说默认路径是 legacy。后半句仍然对。前半句过时：L0/L1/Admission/L2 Bid 与 shadow 记录已经在库里，只是影子且默认关闭。`collaboration.floor.protocol=floor` 仍被配置接受并忽略。
- 旧文 §7 把 EpisodeDecisionRecord 写成观察层产物，没有标明旗标。main 里 ledger 上的 EDR 与 PDR v2 受 `collaboration.ledger.decisionRecords` 控制，默认不写。`round-runtime.ts` 仍会调用影子记录函数，旗标未同时打开时该函数返回 `wrote: false`。另一份回合内 PolicyDecisionRecord 会随 `PersistedRound` 落盘，那是 LIVE 的回合说明，不是 ledger v2，也不是执行真相。执行账 `kind: "execution"` 由 `chat.ts` 直接追加。
- 旧文 §4 把 Handoff 不变量写成正在执行的顺序。合同状态机在 `handoff-contract.ts`，默认 `collaboration.task.handoffContract=false`。关闭时 `task-runtime.ts` 的 `applyTaskHandoff` 仍允许 `owner_transfer`。
- 旧文 §3.4 把 `proactiveBots = !humanStartsNewRound` 写成设置意图的目标映射。代码里这仍是编译等式（`policy-compiler-sections.ts`），不是已经拆开的两个概念。Owner 要求把耦合当成缺口，而不是再加一个字段。
- 旧文 §6 把 Claim 到 Growth 画成认领回路。main 没有 Claim 事件。Growth 缓冲只聚合已有 ledger，且选人、Admission、Bid 都不读它。主动参与（duty、relevance、`proactiveBots`）不等于认领。
- 旧文 §5 把质量门、Facilitator `STOP_LOOP`、强制增量静默写成机制落点。热路径上实际有的是 `redundancy-guard.ts` 和 `chat.ts` 的 `pure_ack` 跳过。`quality-classifier.ts` 只服务影子。状态机事件名 `stop_loop` 没有执行器。
- 旧文 §3.2 的选人阶梯把 Floor Bid 标成「目标」。Bid 模块已经存在，但是 `drivesProductionDecision: false`。生产阶梯仍是 `decision-engine.ts` 的 mention、duty、relevance、可选 wrap。
- 旧文附录把「全仓无实现」留在 G1。以矩阵为准，该格改为「基础设施在，编排主路径不在」。

## 3. 重写后的 Gaps

### G1 Floor 未成为生产编排路径

基础设施已在：`router-l0.ts`、`router-l1.ts`、`admission.ts`、`floor-bid.ts`、`floor-shadow-plan.ts`。`decideParticipants` 只在 `shadowStage` 为 A 或 B 时挂上 `floorShadow`，不替换参与者。`protocol=floor` 未接线。P0 G1 在 `floor-live-cutover.ts` 加了默认关闭的切流门禁：单独的配置布尔不能把 Floor 名单提升为生产发言人。`protocol` 仍不是 `floor`。本项保持开放。

### G2 没有 Episode Runtime，也没有 Beat Controller

已有：Episode 状态机、Episode Store（`collaboration.episodeStore` 默认 false）、`beatIdForEpisode`。没有：驱动这些状态的生产运行时，以及单拍或多拍控制器。`chat.ts` 不调用 Store。P0。

### G3 Facilitator 没有生产控制平面

已有概念：状态 `FACILITATOR_OBSERVE`，事件 `stop_loop`，EDR 的 `facilitator[]`（`authorized`、`denied`、`route_to_task_governance`）。没有：邀请、质询、合流、停环的执行器。协调者 wrap 在决策引擎里仍是可选收口，这与「Coordinator 不等于 Speaker」一致，但不能代替 Facilitator。P0。

### G4 Claim 缺失

没有 Claim 合同、认领事件或认领到 Growth 的闭环。Floor Bid 是意向，不是认领。主动参与也不是认领。DESIGN-ONLY。不是本轮 P0 切流项。

### G5 质量原语在，生产 Quality Gate 不完整

`quality-classifier.ts` 为影子。`redundancy-guard.ts` 与客套跳过在热路径。没有统一的增量门，也没有旧文描述的常态 `STOP_LOOP`。质量保持横切，不另起垂直平面。不是本轮 P0。

### G6 Handoff 已实现且默认关闭

`handoff-contract.ts` 与 `handoff-invariant.test.ts` 在库内。默认旗标关闭，生产仍可走 `owner_transfer` 捷径。不是本轮 P0，本文也不把默认值改成 true。

### G7 Namespace 已实现，生产切流未做

`runtime-namespace.ts` 与迁移脚本在库内。`collaboration.runtimeNamespace` 默认 false，事实路径仍是 legacy。切流手册 N2 仍阻断。P0 的含义是先完成切流门禁，不是在文档 PR 里打开旗标。

### G8 Legacy Primary/Supplement 仍是生产主路径

入口是 `src/gateway/server-methods/chat.ts` 调用 `executeCollaborationRound`。回合状态是 `PRIMARY_*` 与 `SUPPLEMENT_*`。PolicyV1 视图经默认 legacy 车道喂给这个执行器。P0：把它明确标成兼容执行器，而不是删掉或假装已被 Floor 替换。

### G9 `proactiveBots` 仍与 `humanStartsNewRound` 耦合

编译结果 `proactiveBots = !params.humanStartsNewRound`，L1 默认人为开启新回合，因此默认不主动。Owner 要求拆开语义。禁止新增 `proactiveBots2`。主动参与与 G4 Claim 必须分开写。不是本轮 P0。

### G10 `responseMode` 关键字与单一 blocked 语义仍在热路径

`response-mode.ts` 的关键字分类仍进入 `strategy-dispatch.ts`，讨论模板下会影响限额。目标是把它降为意图信号。`busyAgentIds` 只是 `blockedAgentIds` 的别名投影，L0 排除原因仍叫 `blocked`，代码里没有 `executionBlocked`。显式 @ 让 blocked 成员重新 must-admit，这是参与，不是执行授权；观察者被 @ 也不进入。拆分属于后续契约，本文不新增字段。不是本轮 P0。
