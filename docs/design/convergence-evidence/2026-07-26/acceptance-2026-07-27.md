## 为什么要独立验收

被验收方（执行抢救的 agent）自报"完成"不可采信 —— 它的判定依据来自自己的推导链，
自我误判会原样通过。因此验收要满足两点：

1. **不读被验收方的结论**，只从 git 事实重新推导；
2. **可复现**，任何人或任何 agent 重跑都得到同样判定。

原计划由独立子 agent 承担此角色，实际因连续 3 次限流未能启动，改为**把验收固化成脚本**。
这比一次性的 agent 意见更强：判定可被第三方重跑复核，而不是只能相信某次输出。

```bash
python3 docs/design/convergence-evidence/2026-07-26/verify-rescue.py   # 退出码 0=全 PASS
```

脚本全程只读（不 commit / push / 切分支 / 动 stash / 建删 ref / 改文件）。

## 已知局限

- registry 认领判定用的 glob 匹配偏宽松（`docs/design/**` 之类会过度匹配），
  因此"有 owner"可能偏乐观，"无 owner"则是可靠的 —— 方向上偏安全。
- 独立子 agent 验收（人类语言层面的对抗式复核）本轮未能执行，脚本只能覆盖可机械判定的事实；
  设计意图、处置口径是否合理这类判断，仍需人工或子 agent 复核。
