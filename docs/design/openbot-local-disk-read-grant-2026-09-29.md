### 0.2 v0.2 相对 v0.1 的变更

1. 为本场景单独定义能力档案 `local-files-readonly`。节点声明、Gateway 命令策略、节点执行三处同时拒绝 `system.*`。不能只靠隐藏 Agent 工具。
2. 用短期签名能力令牌替换裸 `grantId`。令牌绑定网关、租户、用户、数字人、会话、轮次、设备和路径。
3. 在消息入口生成 `UserDirectedLocalResource`。工具调用时不得重新扫描模型上下文，模型也不得提交 `userDirected=true`。
4. 增加 `LocalDeviceBinding`。路由使用稳定 `nodeId` 与设备公钥，不使用显示名。
5. 节点打开文件时防止检查与读取之间的替换，并从已打开的文件描述符读取。
6. 敏感路径改为三层拒绝，且节点是最后一道执行点。
7. 模型只看见高层工具 `local_file.*` 与 `local_archive.*`。`node.invoke` 只做内部传输。
8. ZIP 使用 `archive.list` / `archive.readEntry`，不解压到磁盘。
9. 主动读取的卡片只保留「允许这一次」和「拒绝」。定向读取时展示一条非阻塞状态。
10. 规定返回结构、大小上限和审计字段。实施顺序改为先绑定与禁 Shell，最后才灰度生产。

### 0.3 复审需要确认的决定

1. `local-files-readonly` 的命令面是否只包含 `fs.stat`、`fs.list`、`fs.read`、`archive.list`、`archive.readEntry`，并且对该设备显式拒绝全部 `system.*`。
2. 能力令牌的签名主体是否为 Gateway，节点是否只验证签名、有效期、`nodeId`、路径和操作，而不再信任模型传入的许可标识。
3. `UserDirectedLocalResource` 是否只从当前入站消息的用户自有文本生成。路径明确但意图不明确时先询问。引用、日志、代码块、附件正文不自动授权。
4. `LocalDeviceBinding` 是否作为「哪台设备、哪个用户、哪些数字人」的唯一路由依据。
5. v0.2 的大小上限（列表 200 项、单次文本 1–2 MiB、单轮累计 5–10 MiB）是否接受。
6. 复审通过后，是否只允许非生产原型，生产配对仍等待原型验收。

v0.2.1 四项协议已通过，见第 7.3 节。第 8 节第 1–7 步可以在非生产环境开工，且必须满足第 9.7 节。第 8–10 步仍关闭。

## 1. 要解决的问题

线上数字人跑在生产网关的工作区里。用户在对话中给出自己电脑上的路径并要求读取时，数字人读不到。文件不在网关那台机器上，网关侧执行也被锁在该数字人的工作区根之内。

要补的能力是一条端到端授权，而不是「节点上多一个读文件函数」：

- 用户在当前这一轮用自己的文本明确指定本机文件，并明确要求读取时，数字人可以直接读取该文件。
- 数字人自己决定去读用户没有指定的路径时，必须先得到一次性授权。
- 读取发生在该用户已绑定的本机节点上。生产网关工作区沙箱保持关闭。
- 从用户、租户、数字人、会话、轮次到设备和路径的绑定不可由模型伪造。

这不是让云端容器挂载用户磁盘，也不是让数字人在网关或本机上执行 shell。

### 1.1 线上证据

对象：生产网关上的 Skill孵化（`bot-skill`）。工作区根形如：

`/root/openbot-tenants/<tenant>/users/<user>/OpenBot/workspace-bot-skill`

2026-09-21，用户发送 `/Users/daniel/Desktop/box-browser-auth-skills.zip`，并要求打开、读取、与已有技能比对。该路径只作为聊天文本到达，没有作为附件上传。随后 `exec` 在碰到工作区外路径时被拒绝，包括 `/dev/null` 重定向。工具错误原文：

`exec denied: shared-fs-resource intersect: Path escapes workspace root (.../workspace-bot-skill): /dev/null`

同一规则拦住了对家目录、`/tmp`、上级 `state`、全盘 `find` 的尝试。数字人能读到的，是更早一次粘贴进对话、已进入网关附件库的技能正文，不是桌面上的 zip。

2026-09-29，用户要求重试，并问「你无法从本地电脑读取文件吗？」。数字人能读自己的工作区、已上传附件和知识库，不能读用户本机桌面。它所说的全盘扫描并不成立，因为大量查找在命令启动前就被拒绝。

### 1.2 本机现状不能直接拿来用

本机 Mac 上已有节点，显示名 `UPBEYOND Mac`，`~/.openbot/node.json` 里登记的网关是 `127.0.0.1:18789`。它连的是这台 Mac 上的本地网关，线上 Skill孵化看不到它。显示名只用于展示，不作为路由键。

本地网关的 `tools.exec` 为 `host=node`、`security=full`、`ask=off`。这是不询问的 shell，不是只读文件。该配置不得复制到生产，也不得作为本方案的样板。

现有 Mac Node Host 连接时声明的命令包含 `system.run.prepare`、`system.run`、`system.which` 和执行审批配置命令（`src/node-host/runner.ts`）。Gateway 对 macOS 的默认命令集合包含完整 `SYSTEM_COMMANDS`（`src/gateway/node-command-policy.ts`）。因此，把这台 Mac 连到生产网关，并不等于只开放文件读取。若配置或工具暴露出现偏差，生产数字人可能同时获得 `system.run`。这是 v0.2 的阻断项。

### 1.3 成功时用户看到什么

以 2026-09-21 那次请求为验收样本：

- 用户在自己的消息正文里写明桌面 zip 的绝对路径，并明确要求读取。不再第二次确认。界面出现一条非阻塞状态：「正在从你的 Mac 读取：~/Desktop/box-browser-auth-skills.zip」。这是可见性，不是审批。
- 节点用 `archive.list` / `archive.readEntry` 返回技能包内容。不解压到磁盘。
- 数字人接着要列出家目录、`~/Downloads` 或扫描其他路径时，出现只含「允许这一次」和「拒绝」的卡片。拒绝或超时则该次读取不发生。
- 用户把文件拖进对话时，仍走附件，不走本机磁盘通道。

## 2. 不在本方案内

- 不放宽生产网关的 `shared-fs-resource` 工作区边界（`src/agents/shared-fs-resource-policy.ts`）。网关进程不读取 `/Users/...`。
- 不把 `system.run` 的 `security` 调成 `full`，也不把 `ask` 调成 `off`。
- 不把知识库「绑定本地文件夹」当作本能力（`src/gateway/knowledge/sources/local-folder-path-policy.ts`）。那是长期索引，默认还限制在 Data Space 内。
- 不提供本机写入、删除、移动、执行。
- 不把历史消息、其他会话、其他数字人、引用块、日志、代码块或附件正文里的路径当成定向许可。
- 不提供「本会话这个目录」。目录级范围通常大于用户感知，长生命周期数字人的「会话结束」也不稳定。
- 不提供「以后一直可读这个目录」。等设备绑定、撤销、会话生命周期和审计页面都存在之后再单独立项。
- 不在复审通过前把 Mac 节点连接到生产网关。

## 4. 方案

### 4.1 端到端顺序

```text
入站用户消息
        |
        v
入口层生成 UserDirectedLocalResource（仅 authored_text）
        |
        v
模型调用 local_file.* 或 local_archive.*
        |
        v
Gateway 签发 resolve-ticket（不许返回内容，不许搜目录）
        |
        v
节点展开 ~、规范化、硬拒绝，只回路径与文件身份
        |
        v
Gateway 用该结果展示审批，或签发本轮 Turn authorization
        |
        v
每次节点调用再派生 useCount=1 的 Invocation capability
        |
        v
节点先验签，再向 Gateway 在线原子兑换 nonce，然后安全打开
        v
元数据与受限内容回到该会话，并写审计
```

v0.2 正文里「Gateway 先写入 canonicalRoot，节点再 realpath」以及「一张 useCount=1 令牌覆盖整次 ZIP」作废，以第 9 节为准。

网关工作区文件、对话附件、知识库检索保持原路径，不经过这张令牌。

### 4.2 能力档案 local-files-readonly

本场景使用独立档案，不改现有 Mac Node Host 的默认命令声明。

节点连接时只声明：

- `fs.stat`
- `fs.list`
- `fs.read`
- `archive.list`
- `archive.readEntry`

Gateway 对该 `nodeId` 的策略：

- 允许上述五条。
- 显式拒绝全部 `system.*`，包括 `system.run`、`system.run.prepare`、`system.which`、`system.notify`、`system.execApprovals.get`、`system.execApprovals.set`。
- 不采用 macOS 平台默认的 `SYSTEM_COMMANDS`。

节点 `handleInvoke` 对档案之外的命令直接拒绝，即使 Gateway 误发。模型工具列表隐藏 `system.run` 不够。验收必须包含：直接构造 `node.invoke(command="system.run")` 失败。

同一台 Mac 上若已有承担本地 shell 的节点，不得把那个进程改声明成只读档案后再拿去连生产。生产用的是只声明上述五条命令的专用节点。本地 `127.0.0.1` 上的现有节点保持原样，直到另有变更单。

### 4.3 设备绑定

```text
LocalDeviceBinding {
  tenantId
  userId
  nodeId
  devicePublicKey
  allowedAgentIds
  capabilityProfile    // v0.2 固定 local-files-readonly
  status               // active | revoked
  createdAt
  revokedAt
}
```

- 路由键是 `nodeId` 加设备公钥身份。显示名只出现在界面。
- `allowedAgentIds` 首期只有 `bot-skill`。
- 未绑定、已撤销、租户或用户不匹配、数字人不在名单内：不调用节点。
- 同一用户多台设备时，使用该用户名下、档案匹配、状态为 active 的绑定。有多台且用户没有选定时，先请用户选定，不广播。
- 生产连接仍暂缓。绑定模型和只读档案先在非生产验证。

### 4.4 能力令牌

v0.2 要求令牌在签发时就带上 `canonicalRoot`，并且整次授权 `useCount=1`、`mode` 只有 `file`。这三项在 v0.2.1 作废，协议见第 9 节：

- Gateway 不能在自己的机器上规范化 Mac 路径。节点在没有票据之前也不对任意路径做 `realpath`。
- 一次 ZIP 比对需要 `archive.list` 加多次 `archive.readEntry`，不能挤在一张单次令牌里。
- 节点重启会丢掉内存中的 nonce。消费记录放在 Gateway 在线兑换，不放在节点内存。
- 目录的一次 `list` 用 `targetKind=directory` 与 `scope=exact` 表达，不引入目录树授权。

### 4.5 入口层的本轮资源记录

`before_tool_call` 适合拦截，不能从工具参数反推用户是否点名。入口在接受本轮用户消息时生成：

```text
UserDirectedLocalResource {
  inboundMessageId
  userId
  tenantId
  sessionKey
  nodeId
  rawPathSpan {
    startOffset
    endOffset
    sourceKind          // 只有 authored_text 可生成定向许可
    normalizedInput
  }
  requestedIntent       // read | list | inspect-archive | unspecified
  createdAt
}
```

规则：

- 只使用消息平台已经解析出的用户自有正文。`sourceKind` 必须是 `authored_text`。
- 引用、转发、日志、代码块、附件正文不生成定向记录。渠道给不出这些区段的结构时，本条消息不生成定向许可。
- 不用正则从最终拼接文本里猜测区段。
- 路径明确，且同一片段的意图是打开、读取、查看、比对这个文件：`requestedIntent=read`，可以免二次确认。
- 路径明确，但意图不明确：`requestedIntent=unspecified`，先询问，不直接读。
- 没有路径：不生成记录。数字人追问路径或请用户上传，不搜索磁盘。
- 一条消息点名多个文件：每个文件一条记录。不自动提升到它们的公共父目录。
- 工具调用时只读取已经挂在本轮执行上下文上的记录。不重新扫描整段模型上下文。

2026-09-21 的桌面 zip 消息属于「路径明确且要求读取」，应对应一条 `requestedIntent=read` 的记录。

### 4.6 高层工具

不把本能力放进 `nodes` 的 `action=invoke`。该入口接受任意 `invokeCommand`（`src/agents/tools/nodes-tool.ts`），范围过大。

模型可见的工具：

- `local_file.stat`
- `local_file.list`
- `local_file.read`
- `local_archive.list`
- `local_archive.read_entry`

这些工具在 Gateway 侧完成：绑定当前租户、用户、数字人、会话和轮次；选择已绑定节点；对照 `UserDirectedLocalResource`；申请或消费能力令牌；经内部 `node.invoke` 调用；按第 4.10 节限制返回。

通用 `nodes` invoke 不能凭命令名调用 `fs.*`、`archive.*` 或 `system.*` 来绕过这些工具。Gateway 对 `local-files-readonly` 设备拒绝来自通用 invoke 的调用。

### 4.7 归档读取

`fs.read` 返回 ZIP 原始字节，不能完成技能比对。ZIP 使用：

- `archive.list`
- `archive.readEntry`

禁止把 ZIP 解压到磁盘。节点在内存或临时只读视图中处理，并拒绝：

- Zip Slip（条目路径逃出归档根）
- 压缩炸弹与异常压缩比
- 超过上限的展开大小、条目数、嵌套归档
- 条目名中的绝对路径、`..` 和路径分隔符穿越

条目内容适用与普通文件相同的敏感类型拒绝和上下文大小限制。

### 4.8 节点上的安全打开

先 `realpath` 再按路径读取，挡不住检查和打开之间的替换。节点对每次访问：

- 对目标及每一级父目录执行 `lstat` / `realpath`，逐级确认没有离开许可根。
- 打开时使用不跟随符号链接的标志。
- 打开后 `fstat`，确认类型、设备号和 inode 与检查结果一致。
- 从该文件描述符读取，不按路径再读一次。
- 目录列举只取直接子项。子项名称不得包含路径分隔符。
- 拒绝目录项在 `list` 之后被替换成另一对象再读内容：读之前重新按上述步骤打开，不信任先前 `list` 的结果。
- 拒绝特殊文件、设备、FIFO、Unix socket。只接受普通文件和目录。

Gateway 可以先拒绝明显越界路径，以缩短等待。节点上的检查是执行防线。

### 4.9 三层拒绝

任何授权，包括用户点名和「允许这一次」，都不能打开硬拒绝对象。

1. **系统硬拒绝路径。** 至少包括：`~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.kube`、`~/.docker`、`~/.openbot` 中的凭据与令牌、钥匙串、其他用户的家目录、`/System`、`/private/etc`。云厂商、Kubernetes、Docker 凭据目录按同一层处理。
2. **敏感文件名与类型。** 至少包括：私钥、`.env`、`.npmrc`、`.pypirc`、Git credential / helper、浏览器 profile 中的 Cookies 与 Login Data、Messages 与 Mail 数据库、socket、设备文件。匹配发生在规范化路径和最终 inode 两侧。
3. **普通用户内容。** Desktop、Downloads、Documents 等才进入定向读取或一次性授权。不在第 1、2 层，也不等于默认可读；仍要有本轮点名或一次性批准。

硬拒绝在节点执行。Gateway 提前拒绝只为了少一次往返。用户若要提交秘密文件，走附件上传，不走本通道。

### 4.10 返回与上限

`fs.read` 不把原始字节无条件送进模型上下文。节点返回：

- 文件名、大小、MIME、修改时间
- SHA-256
- 是否文本、编码检测结果
- 已返回的字节范围、是否截断
- 文本内容，或安全的结构化提取结果

初期上限：

| 项           | 上限                                                                                                                                |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `fs.list`    | 最多 200 项，不递归                                                                                                                 |
| 单次文本读取 | 业务层 1–2 MiB。WebSocket 单帧上限约 25 MiB（`src/gateway/client.ts`、`src/gateway/server-constants.ts`），不能把帧上限当成读取上限 |
| 单轮累计读取 | 5–10 MiB                                                                                                                            |
| 二进制文件   | 默认只返回元数据，交给专用解析器                                                                                                    |
| ZIP          | 限制条目数、单条展开大小、总展开大小和压缩比                                                                                        |

禁止用连续分片把单轮累计上限拆开绕过。超过上限时返回截断标记和总大小，不自动续读。

### 4.11 主动读取的审批

路径不在本轮 `requestedIntent=read` 的记录内时，不访问磁盘。复用现有审批的挂起、超时和拒绝回退，类型独立于 shell 审批。

卡片展示数字人、规范化绝对路径、操作类型。按钮只有：

| 按钮       | 结果                                                 |
| ---------- | ---------------------------------------------------- |
| 允许这一次 | 签发 `useCount=1` 的能力令牌，只覆盖该路径上的该操作 |
| 拒绝       | 不签发。工具结果为拒绝                               |

界面不可达、关闭或超时：拒绝。不默认允许。

定向读取不弹这张卡片。界面只显示非阻塞状态，例如「正在从你的 Mac 读取：~/Desktop/example.zip」。

### 4.12 审计

每次授权决定和每次读取写审计，至少包括：

- 用户、租户、数字人、会话、入站消息 ID
- 节点稳定 ID
- 操作，以及规范化路径的哈希和有限脱敏展示
- 许可来源：`user-directed` 或 `user-approved-once`
- 决策结果与拒绝原因
- 返回字节数、文件哈希、是否截断
- 时间、耗时、错误代码

不记录文件内容、凭据或完整能力令牌。运营日志不记录完整本机路径。

## 5. 失败与滥用

| 情况                                              | 行为                                   |
| ------------------------------------------------- | -------------------------------------- |

## 9. v0.2.1 协议补丁

本节只闭合复审点名的四项。第 4 节与本节冲突时，以本节为准。已通过的能力档案、设备绑定、入口证据、高层工具、ZIP 不落地、安全打开、三层拒绝、一次性卡片、返回限额和审计保持有效。

现有 WebSocket 单帧上限约 25 MiB。业务层单次读取仍限制在 1–2 MiB，不把帧上限当成文件读取上限。

### 9.1 两阶段路径解析

Gateway 不能在网关机器上规范化 Mac 路径。`~` 只能由目标节点按绑定用户展开。符号链接、文件是否存在、真实路径都只存在于节点文件系统。节点在拿到允许解析的票据之前，不对任意路径执行 `realpath` 或 `stat`。

1. Gateway 签发短期 `resolve-ticket`。它绑定原始用户路径、`nodeId`、用户、会话、轮次和打算进行的操作。它不允许返回文件内容，也不允许列目录或搜索。
2. 节点用现有命令 `fs.stat`，且 `capabilityType=resolve-ticket`。不新增 `fs.resolve`。此模式只能展开并规范化票据上的一个路径、执行硬拒绝，并向 Gateway 返回规范化路径、类型和文件身份。不列目录，不返回正文，不计算内容哈希，不接受 glob，不搜索相邻路径。
3. Gateway 用这个结果展示审批卡片，或在用户本轮已经明确授权时签发第 9.2 节的 Turn authorization。卡片上的路径来自节点返回值，不来自 Gateway 自己的字符串拼接。
4. 最终读取时节点按第 4.8 节再次安全打开，并核对文件身份。resolve 阶段的结果不长期有效。身份不一致则拒绝，不沿用旧 inode。读取前 inode 被替换时，读取失败，预算与审计状态保持一致，不把失败伪装成未发生。

`resolve-ticket` 同样是 Gateway 签名的短期票据，一次一路径，`useCount=1`，经第 9.3 节兑换。它不能派生读取能力。命令集合仍是精确五项。解析失败、路径不存在或命中硬拒绝时，对模型只返回统一的「该位置不可授权」，不改去搜索相邻路径。

主动审批发生在用户批准之前。规范化结果只进入授权卡片，不作为工具结果返回模型，不告知路径是否存在，不返回大小、inode 或类型。硬拒绝同样只向模型返回「该位置不可授权」。否则模型可以反复触发 resolve 探测磁盘结构。

用户定向读取已有本轮授权证据，resolve 之后可以继续建立 Turn authorization，并把该次读取所需的结果交给模型。

### 9.2 两层授权

用户的一次意图是一层，每一次节点调用是另一层。

**Turn authorization** 由 Gateway 保存并签名，表示本轮允许对一个已解析目标做一组有界操作：

| 字段                                                    | 含义                         |
| ------------------------------------------------------- | ---------------------------- |
| `turnId` / `messageId`                                  | 本轮                         |
| `nodeId` / 租户 / 用户 / `agentId` / `sessionKey`       | 绑定                         |
| `canonicalPath`                                         | resolve 返回的路径           |
| `fileId`                                                | resolve 返回的设备号与 inode |
| `targetKind`                                            | `file` 或 `directory`        |
| `scope`                                                 | 只有 `exact`                 |
| `operations`                                            | 允许的操作集合               |
| `maxEntriesRead` / `maxTotalExpandedBytes` / `maxCalls` | 本轮预算                     |
| `expiresAt`                                             | 本轮结束即失效               |

**Invocation capability** 由 Gateway 为每一次 `node.invoke` 从 Turn authorization 派生。每张仍然 `useCount=1`、独立 nonce。节点不接受没有 Invocation capability 的读取。派生不得超出 Turn authorization 的操作集合和剩余预算。

`targetKind` 与 `scope`：

- `file` + `exact`：只允许该文件。
- `directory` + `exact` + `operation=list`：只允许列出该目录的直接子项，最多 200 项，不递归。
- 列出的子项不自动获得读取权限。要读某一个子项，必须有对该文件的新一轮点名，或一张新的一次性批准。
- 不存在 `directory-tree`，也不存在递归目录授权。「本会话这个目录」仍然不做。

定向读取一个 ZIP 时，Turn authorization 的有界任务是「检查这个 ZIP」，而不是一张只够 `archive.list` 的令牌。默认预算：

- `operations = [archive.list, archive.readEntry]`
- `maxEntriesRead = 30`
- `maxTotalExpandedBytes = 5 MiB`
- `maxCalls = 32`

界面若显示「正在读取这个 ZIP」，实际批准的就是上述有界任务。不得显示「读取文件」而只批准第一次 `archive.list`。

主动审批的「允许这一次」必须写明批准的是哪一种：

- 单一操作，例如「列出这个目录」：`operations=[list]`，`targetKind=directory`，`scope=exact`。
- 有界任务，例如「检查这个 ZIP」：使用上面的 ZIP 预算。

用户拒绝或超时，不签发 Turn authorization。预算耗尽后，本轮不再派生新的 Invocation capability。

### 9.3 防重放与签名

节点内存里的 nonce 集合在进程重启后会丢失，不能当作已消费记录。非生产原型使用 Gateway 在线原子兑换：

1. 节点先验签、核对 `nodeId`、有效期、操作和路径。验签失败不联系兑换接口。
2. 验签通过后，向 Gateway 提交完整 Invocation capability，而不是只提交 nonce。兑换键至少是 `capabilityDigest + nonce + nodeId`。
3. Gateway 在同一事务内再次验证并完成兑换，见下方清单。任一失败则整笔拒绝，不先污染 nonce 记录。
4. 兑换成功后，节点才安全打开并返回数据。打开失败时不自动重新签发，也不静默重试。
5. 断线重连与进程重启都不清除 Gateway 上未过期的已消费记录。

Gateway 兑换端必须验证：

- 完整 Invocation capability 签名与 `keyId`
- `nodeId`，以及当前已认证节点连接的设备公钥
- 租户、用户、agent、session、turn
- operation 与 capability 哈希
- 该 capability 确实由仍有效的 Turn authorization 派生
- 剩余预算，并在同一事务内扣减
- nonce 尚未消费，并在同一事务内标记已消费

兑换事务的步序固定为四步，全部在同一事务内，顺序不可调换：

1. 验证 capability，即上面清单的全部项。
2. 检查并扣减对应 Turn authorization 的剩余预算。
3. 标记 nonce 已消费。
4. 返回一次性兑换成功结果。

验证必须发生在任何写入之前。任一步失败即整笔回滚：预算不扣减，nonce 不记为已消费，不返回成功。兑换成功结果本身也是一次性的，重复提交同一 `capabilityDigest + nonce + nodeId` 不再返回成功。

只提交 nonce、篡改 capability，或从错误的节点连接发起兑换，一律拒绝。两个节点同时兑换同一 capability 时，只有绑定节点成功，且只成功一次。Turn authorization 已撤销或预算耗尽时，即使 Invocation capability 尚未过期，兑换也失败。

签名与密钥：

| 项       | 规定                                                                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 算法     | Ed25519                                                                                                                                                                          |
| 信任方向 | Gateway 签发，节点验证。这不是设备连接签名。设备身份已用 Ed25519 并由公钥派生设备 ID（`src/infra/device-identity.ts`），只复用格式和工具，不复用同一把密钥                       |
| `keyId`  | 每把 Gateway 签名公钥一个标识。令牌带头 `keyId`。节点只接受仍在发布集合中的 `keyId`                                                                                              |
| 轮换     | 新密钥先发布、再签发；旧密钥在最长令牌寿命结束后移出验证集合                                                                                                                     |
| 时钟     | 最大偏差 60 秒。超出 `expiresAt` 加偏差的令牌拒绝                                                                                                                                |
| 泄漏撤销 | 从验证集合移除 `keyId`。已签发、未过期的令牌随该密钥立即失效。在线节点立即收到新的验证集合，不等进程重启。不依赖节点本地黑名单                                                   |
| 信任根   | 节点在首次配对时固定 Gateway 验证公钥的信任根。keyset 更新必须由旧信任根或这条已认证的设备连接保护。未知 `keyId` 不得向调用参数临时要公钥。keyset 过期且无法刷新时，拒绝新的读取 |
| 保存时长 | nonce 至少保存到对应令牌 `expiresAt` 加时钟偏差。过期后 Gateway 删除。节点不持久化 nonce                                                                                         |

resolve-ticket、Turn authorization、Invocation capability 使用同一签名体系。三者的 nonce 空间分开，不能用解析票据的 nonce 去兑换读取。

### 9.4 目录列表与文件读取的边界

一次「列出 ~/Downloads」在 resolve 成功且用户批准「列出这个目录」之后，只发生一次 `local_file.list`。子项名称返回给模型和用户，但每个子项的 `read` 仍要单独授权。用户本轮原文如果点名的是文件而不是目录，`targetKind` 只能是 `file`，不能改成对该父目录的 `list`。

### 9.5 随协议必须定死的配套规则

这些规则不改变已通过的架构，但两阶段解析和专用节点如果不定死，实现时会走旁路。

**能力档案是连接身份的一部分。** 节点自己声明的命令不是安全档案。连接进入 `active` 前，下列五项必须精确相等，多一个或少一个都拒绝：

- `LocalDeviceBinding.capabilityProfile = local-files-readonly`
- 设备公钥身份与绑定一致
- Node Host 启动配置中的档案
- 节点声明的命令集合
- Gateway 期望的命令集合：`fs.stat`、`fs.list`、`fs.read`、`archive.list`、`archive.readEntry`

现有白名单集中在 `resolveNodeCommandAllowlist`（`src/gateway/node-command-policy.ts`）。专用档案在该入口扩展，不把这五条命令加进 macOS 默认 `SYSTEM_COMMANDS`。

**同一台 Mac 上的两个节点进程。** 本地 Gateway 的 shell 节点与生产只读节点不得共用默认身份或配置。原型前各自独立：

| 项                      | 只读节点                             | 现有 shell 节点          |
| ----------------------- | ------------------------------------ | ------------------------ |
| 配置文件                | 单独路径                             | 保持现状，不改           |
| 身份密钥                | 单独的设备密钥                       | 不共用                   |
| LaunchAgent 名称        | 单独标签                             | 不共用 `ai.openbot.node` |
| 日志、PID、锁、数据目录 | 单独目录                             | 不共用                   |
| Gateway 地址            | 非生产原型指向非生产网关             | 继续 `127.0.0.1:18789`   |
| 卸载与撤销              | 单独命令，撤销时把绑定标为 `revoked` | 不因只读节点卸载而停止   |

生产地址不在原型配置里填写。

**路径比较覆盖 macOS。** resolve 与最终打开都处理：APFS 默认大小写不敏感；Unicode NFC/NFD；`/Users` 与 `/System/Volumes/Data` 的同一文件；Finder alias 不等于普通符号链接，原型拒绝 alias。读取过程中文件被截断或增长时，以打开后的 `fstat` 和实际读到的范围为准，并在结果里标明。

普通读取对象的 `nlink > 1` 时默认拒绝，不进入自动定向读取。只核对最终路径名和 inode 类型，发现不了同一 inode 还链在敏感目录里。归档条目适用与普通文件相同的敏感文件名和内容类型限制。ZIP 位于 Desktop，不能因此放行其中的 `.env`、私钥或 credential 数据。

原型只允许本地普通卷。外接磁盘、磁盘映像和网络文件系统默认拒绝，以后单独评估。

### 9.6 补进验收的协议用例

在第 6 节之外增加：

1. Gateway 在未收到 resolve 结果前不签发带真实路径的读取令牌。节点在没有 resolve-ticket 时不对路径做 `stat`。
2. 一张「检查这个 ZIP」的 Turn authorization 可以完成一次 `archive.list` 和限额内的多次 `archive.readEntry`。每次调用的 nonce 不同。超出 `maxEntriesRead`、`maxTotalExpandedBytes` 或 `maxCalls` 后拒绝。
3. 卡片写「列出这个目录」时不能读子项内容。卡片写「检查这个 ZIP」时不能只批准 `archive.list`。
4. 节点进程重启后，重放尚未过期的 Invocation capability。Gateway 兑换失败，节点不读盘。
5. 使用已撤销 `keyId` 签名的令牌。节点先验签失败，且不发起兑换。
6. 声明命令比档案多一条或少一条。连接不进入 `active`。
7. 外接盘或网络挂载上的路径。resolve 拒绝。
8. 同一文件经 `/Users/...` 与 `/System/Volumes/Data/Users/...` 解析。文件身份一致才视为同一目标。
9. 渠道没有结构化区段时，不生成 `sourceKind=authored_text` 的定向许可。
10. 未获批准时，模型反复请求普通路径的 resolve。模型不能得知路径是否存在，也拿不到大小、inode 或类型。
11. 兑换请求只提交 nonce、修改了 capability，或来自错误的节点连接。Gateway 拒绝，且不把该 nonce 记成已消费。
12. 两个节点同时兑换同一 capability。只有绑定节点成功，且只成功一次。
13. Invocation capability 仍在有效期内，但对应 Turn authorization 已撤销或预算耗尽。兑换失败。
14. 敏感文件经硬链接出现在 Desktop。节点拒绝读取。
15. Gateway keyset 无法刷新，或令牌使用未知 `keyId`。fail closed，不向调用参数索取公钥。
16. resolve 成功且审批完成，但读取前 inode 被替换。读取失败，预算与审计状态一致。
17. 节点兑换成功后文件打开失败。不自动重新签发，也不静默重试。

### 9.7 非生产实现的 P0

批准开工不等于可以放宽下列条件。实现和测试都要覆盖，缺一项不算第 7 步通过。

| P0               | 要求                                                                                                                                                          | 位置      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| resolve 命令     | 使用 `fs.stat` 且 `capabilityType=resolve-ticket`。不新增 `fs.resolve`。不列目录、不回正文、不算内容哈希、不接受 glob、不搜索相邻路径                         | 第 9.1 节 |
| 兑换再次验签     | Gateway 在同一事务内验证完整 capability、绑定、派生关系和剩余预算，并扣减预算、消费 nonce。兑换键至少是 `capabilityDigest + nonce + nodeId`。不能只提交 nonce | 第 9.3 节 |
| resolve 不进模型 | 用户批准前，规范化结果只进授权卡片。模型得不到是否存在、大小、inode 或类型。硬拒绝统一为「该位置不可授权」                                                    | 第 9.1 节 |
| 硬链接与归档     | `nlink > 1` 默认拒绝。ZIP 内的敏感文件名和内容类型照样拒绝                                                                                                    | 第 9.5 节 |
| keyset           | 首次配对固定信任根。更新走旧信任根或已认证设备连接。无法刷新或未知 `keyId` 时拒绝。撤销后在线节点立即更新                                                     | 第 9.3 节 |
