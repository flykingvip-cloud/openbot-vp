## 0. 证据边界（必须保留）

调查足以支持登记一个**架构与产品契约对齐问题**，但「设计文档描述了 index」还**不足以**证明所有可管理文件都承诺即时参与当前 `manager.search`。

- **不得**把 Data Space 模型 v1 的 index 叙事直接当作已确认的线上故障。
- O5「删 A 后同来源残留」在 A 从未进入 search 语料时**不可证伪**；该缺口是范围对齐问题，不是本批遗忘缺陷开关。
- 本方案引用调查结论为**源码/文档只读**证据；不构成生产召回验收。

## 2. 三种路径比较（不预选）

### 路径 1 — 管理面收敛到已索引来源

**做法**：Memory Center / 数据目录「可管理记忆」列表与忘记目标，收敛为与 `manager.search` 已索引语料一致的集合（主要为 workspace `MEMORY.md` / `workspace/memory/**`，及已配置的 sessions/collaboration）。

| 维度       | 影响                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------- |
| 来源身份   | 管理 key 与 indexed relPath / sourceIdentity 对齐；减少「能删不能搜」的双身份               |
| 租户权限   | 仍走现有 agent 所有权 / Memory Center ACL；范围缩小后权限面更易推理                         |
| 重复内容   | 降低 DS 副本与 workspace 副本并行展示造成的「删一留一」误解                                 |
| 迁移       | 需处理历史 DS `memory/agent` 中仅管理面可见的文件：归档、一次性迁入 workspace、或只读遗留区 |
| 成本       | 索引与 embedding **不**扩大；主要是 UI/文案/forget 候选路径收窄                             |
| 删除一致性 | forget 目标 ⊆ 已索引集合后，更容易定义「删文件 + 可选撤索引」的完成态                       |

**优点**：与现行 search 实现一致；不扩大召回面。  
**风险**：削弱模型叙事中 DS memory 子树作为一等资产的管理入口；迁移期用户可见「文件去哪了」。

### 路径 2 — 将符合权限的 Data Space 来源纳入索引

**做法**：在 ACL / 租户边界内，把 `MEMORY_SCAN_ROOTS`（或子集）纳入 `listIndexedDocuments` / CogniWeave 摄入，并使 forget 更新或撤回对应 index。

| 维度       | 影响                                                                                    |
| ---------- | --------------------------------------------------------------------------------------- |
| 来源身份   | 需稳定 sourceIdentity：DS 绝对/相对路径、agentId、与 workspace 路径撞车时的去重键       |
| 租户权限   | personal vs agent vs workspace 扫描根必须强制隔离；enterprise 不得经 MC 扩读员工私有 DS |
| 重复内容   | 同文案可并存于 DS 与 workspace → 必须定义去重 / 多源 atom / 双命中 UX，否则召回噪声上升 |
| 迁移       | bootstrap「MEMORY.md → memory/agent」与反向「索引纳入」需单一事实来源，避免双写放大     |
| 成本       | embedding / FTS / syncScope 成本上升；大库首次纳入与增量 watch 需预算                   |
| 删除一致性 | 忘记必须串联索引撤回 / lifecycle，否则「文件已删仍命中」成为真缺陷                      |

**优点**：更贴近模型 §4「memory + index」。  
**风险**：召回扩大、权限与去重复杂；**本文件不预选**此路径。Owner 已否决「仅为 O5 可测」而扩索引。

### 路径 3 — 明确区分「文件归档管理」与「可检索记忆」

**做法**：产品与文案上拆成两套对象：

1. **归档/文件管理**：DS 扫描根上的文件 list/forget（现行 MC 文件面）。
2. **可检索记忆**：workspace（等）已索引语料及原子/证据视图。

明确声明：管理面删除 ≠ 保证 search 消失；search 命中 ≠ 管理面必有对应 DS 文件。

| 维度       | 影响                                                         |
| ---------- | ------------------------------------------------------------ |
| 来源身份   | 两套 ID 空间并存，但**命名与 UX 不再暗示等价**               |
| 租户权限   | 各面沿用现 ACL；不因「看起来像同一记忆」而合并授权           |
| 重复内容   | 允许双副本；用文案消歧（O5 已统一文件删除提示方向）          |
| 迁移       | 可不迁数据；可选提供「提升为可检索」显式动作（另批）         |
| 成本       | 最低工程成本；无强制 reindex                                 |
| 删除一致性 | 契约变为「按面删除」；全来源事实级遗忘仍为**待评估**独立需求 |

**优点**：诚实对齐现状；快速消除虚假缺陷叙事。  
**风险**：与模型 §4 长期文案仍张力，需在架构债中保留「若未来要统一，走路径 1 或 2」的指向。

## 3. 横切对照表

| 议题       | 路径 1 收敛管理面 | 路径 2 扩索引       | 路径 3 明确分层   |
| ---------- | ----------------- | ------------------- | ----------------- |
| 来源身份   | 单侧对齐 indexed  | 需新 DS 身份与去重  | 双身份显式并存    |

| 成本       | 低（产品/UI）     | 高（索引/同步）     | 最低              |
| 删除一致性 | 易与索引对齐      | 必须做才合格        | 按面定义，不混称  |
