## 3. 独立存储与日志位置

原则如下（对隔离实现与未来经批准的部署都适用，但本方案不在现网创建这些目录）：

- A′ 存储目录与 B′ 存储目录必须互相独立，也不得指向生产 `/var/lib/openbot` 或私有 soak 数据目录。
- 每个目录同时只允许一个协议进程打开（单写入者）。第二实例必须启动失败。
- 日志写在各自主机的独立文件或 journal，保留完整请求 ID、任务 ID、租约 subject、对账审计字段。
- 备份若需要，只能在隔离盘或另行批准的隔离目标，不得写回生产盘。

当时建议的路径形态（示例，**已取消，不得在现网创建**）：

- A′ 存储：`/var/lib/openbot-iso-a/exec-store`
- A′ 日志：`/var/log/openbot-iso-a/`
- B′ 存储：`/var/lib/openbot-iso-b/exec-store`
- B′ 日志：`/var/log/openbot-iso-b/`

## 4. 故障注入与恢复方法

下列操作原先只允许在隔离双机上执行。**专项隔离双机不会开通，这些故障注入不得拿到现网四台服务器上做。** 隔离实现已用同机/同盒测试覆盖其中若干行为，但那些测试不能替代未来真实 A/B 部署后的基本验收。

| 场景             | 操作要点                                                        | 恢复要点                                                         |
| ---------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- |
| 断链             | 在隔离网络上阻断 A′→B′（临时防火墙或接口关闭），不得改生产路由  | 恢复隔离通路后，只允许查询/对账/重试只读同步，不得自动重跑原任务 |
| 重启 A′          | 优雅停止后再拉起同一存储目录的单一实例                          | 锁必须释放并可重新获取；已提交任务不得因重启再开第二跑           |
| 重启 B′          | 同上；在途任务按协议进入或保持 `result_unconfirmed`，不得当成功 | 重启后不得重放执行；未确认结果走对账入口                         |
| 提交响应丢失     | 在 B′ 已接受但响应未回到 A′ 时中断                              | A′ 按幂等键查询，不得再提交出第二个任务                          |
| 取消竞态         | 执行即将成功时发出取消                                          | 最终只能是成功、取消或 `result_unconfirmed` 之一，禁止双终态     |
| 成果中断         | 传输中切断连接或篡改摘要/字节数                                 | 不得标记 `delivered=true`，不得进入 `succeeded`                  |
| 对账后不重复执行 | 经 A′ 对账进入终态或保持未确认后，再提交同一意图或再次对账      | B′ 执行次数不增加                                                |

## 5. 专项跨机验收清单（已取消；各项为 UNVERIFIED）

下列必测项与当时 t126 双机验收清单对齐，予以保留以便追溯。专项跨机验收已取消且从未执行，因此各项结果必须标记为 **UNVERIFIED**，不得记为 PASS，也不得改记为「等待新虚机后继续」的 BLOCKED。不得把同机测试记为跨机通过。

1. 正常任务：A′ 提交，B′ 实际执行，成果完整校验通过后可下载。
2. B′ 不可达时 A′ 不得执行原任务，也不得把主机回落当成成功。
3. 并发幂等：同一租户同一幂等键并发重复提交，只产生一个任务、一次执行。
4. 提交响应丢失后的恢复，不得产生第二跑。
5. A′ 与 B′ 分别异常退出/重启后的状态与恢复；待同步记录继续处理直至 `synced` 或 `sync_conflict`。
6. 取消与成功竞态；最终只能有一个终态。
7. 成果传输中断与摘要/字节错误，不得假交付。
8. A′ 已提交对账结论后、B′ 收到 apply 前断链：A′ 保持已提交结论与 `pending_sync`，不得重跑原任务。
9. **连通恢复后自动完成同步**：通路恢复后，无需重启 A′/B′ 协议进程，也无需人工或测试代码调用 `resumePendingReconcileSyncs()`，调度器须把 `pending_sync` 处理到 `synced`（或永久冲突则 `sync_conflict`）。本项曾为跨机必测项，现为 UNVERIFIED。
10. B′ 已应用对账但响应丢失：A′ 重试必须幂等，最终为 `synced`，B′ 不得二次执行或出现双终态。
11. 重复、越序和冲突对账请求进入正确状态：同一 `reconcileRequestId` + 同一结论摘要幂等；摘要冲突或越序关闭性结论由 B′ 按本地前置条件拒绝，永久冲突进入 `sync_conflict`，不得自动重试。
12. 所有场景均不得再次执行原任务；同步未完成前也不得提交与已提交结论冲突的状态变更。
13. 强制终止持锁进程后，新进程可以恢复存储与唯一写入者锁；回收残留套接字时不得偷走存活实例的锁。写入中断后的存储恢复不得只覆盖正常 close 后再打开。

每项若将来在经批准的真实 A/B 部署后补做基本验收，证据须包含：双方节点身份、完整代码 SHA、时间线、任务 ID、同步状态、完整校验和，以及监听与认证方式、可复现命令、完整输出、存储与日志位置。当前没有这类跨机证据。

当前状态：**专项跨机验收未跑，结果为 UNVERIFIED**（任务已取消；新隔离机不会开通；现网四台机器不得当作隔离试验场）。同机进程内或同盒双进程测试不能作为本清单的通过证据。真实部署验收不得把执行接口裸露到公网。变更单见 `docs/exec-protocol/v1-two-node-change-ticket.md`（状态：已取消，不得执行）。
