## 1. 节点身份与依赖

建议两台专用隔离机器（名称暂记为 A′-iso、B′-iso），与生产香港 LIVE、私有 soak、生产或预分配的 A/B/C 严格分离。

| 项       | A′-iso                                                 | B′-iso                         |
| -------- | ------------------------------------------------------ | ------------------------------ |
| 角色     | 控制面（协议 A′）                                      | 执行面（协议 B′）              |
| 代码版本 | PR #272 待审完整 SHA，双方必须一致                     | 同左                           |
| 运行时   | Node.js（与隔离测试已用大版本一致，实施时写实）        | 同左                           |
| 进程     | `OPENBOT_EXEC_PROTOCOL_ROLE=a`                         | `OPENBOT_EXEC_PROTOCOL_ROLE=b` |
| 依赖     | 协议进程所需 Node 依赖；不部署生产网关、不挂生产数据盘 | 同左；不启用 host 回落         |
| 存储     | 仅本机独立目录，禁止与 B′ 或任何生产目录共享           | 仅本机独立目录                 |

在变更单批准并完成安装前，不把具体主机名、内网地址或账号写入实施命令。若最终使用的隔离资源与本表不符，须先改本方案再实施。

## 3. 独立存储与日志位置

实施时在变更单中写实绝对路径，原则如下：

- A′ 存储目录与 B′ 存储目录必须互相独立，也不得指向生产 `/var/lib/openbot` 或私有 soak 数据目录。
- 每个目录同时只允许一个协议进程打开（单写入者）。第二实例必须启动失败。
- 日志写在各自主机的独立文件或 journal，保留完整请求 ID、任务 ID、租约 subject、对账审计字段。
- 备份若需要，只能在隔离盘或另行批准的隔离目标，不得写回生产盘。

建议路径形态（示例，非实施命令）：

- A′ 存储：`/var/lib/openbot-iso-a/exec-store`
- A′ 日志：`/var/log/openbot-iso-a/`
- B′ 存储：`/var/lib/openbot-iso-b/exec-store`
- B′ 日志：`/var/log/openbot-iso-b/`

## 4. 故障注入与恢复方法

下列操作只允许在隔离双机上执行，并由变更单写明具体命令与恢复步骤后再做。

| 场景             | 操作要点                                                        | 恢复要点                                                         |
| ---------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- |
| 断链             | 在隔离网络上阻断 A′→B′（临时防火墙或接口关闭），不得改生产路由  | 恢复隔离通路后，只允许查询/对账/重试只读同步，不得自动重跑原任务 |
| 重启 A′          | 优雅停止后再拉起同一存储目录的单一实例                          | 锁必须释放并可重新获取；已提交任务不得因重启再开第二跑           |
| 重启 B′          | 同上；在途任务按协议进入或保持 `result_unconfirmed`，不得当成功 | 重启后不得重放执行；未确认结果走对账入口                         |
| 提交响应丢失     | 在 B′ 已接受但响应未回到 A′ 时中断                              | A′ 按幂等键查询，不得再提交出第二个任务                          |
| 取消竞态         | 执行即将成功时发出取消                                          | 最终只能是成功、取消或 `result_unconfirmed` 之一，禁止双终态     |
| 成果中断         | 传输中切断连接或篡改摘要/字节数                                 | 不得标记 `delivered=true`，不得进入 `succeeded`                  |
| 对账后不重复执行 | 经 A′ 对账进入终态或保持未确认后，再提交同一意图或再次对账      | B′ 执行次数不增加                                                |

## 5. 跨机验收清单（待双机就绪后出具证据）

至少覆盖：

1. 真实执行：A′ 提交，B′ 实际执行，成果校验通过后可下载。
2. 并发幂等：同一租户同一幂等键并发重复提交，只产生一个任务、一次执行。
3. A′ 重启与 B′ 重启后的状态与幂等。
4. 提交响应丢失后的恢复，不得产生第二跑。
5. 取消与成功竞态。
6. 成果传输中断与摘要/字节错误，不得假交付。
7. 对账后不重复执行；负向：无对账角色、过期版本、仅「取消已发送」不能确认取消、无完整成果不能确认成功、无法确认时保持 `result_unconfirmed`。
8. A′ 已提交对账结论后、B′ 收到 apply 前断链：A′ 保持已提交结论与 `pending_sync`，恢复通路后只通过幂等同步完成，不得重跑原任务。
9. B′ 已应用对账但响应丢失：A′ 重试必须幂等，最终为 `synced`，B′ 不得二次执行或出现双终态。
10. A′ 与 B′ 分别重启后，待同步记录继续处理直至 `synced` 或 `sync_conflict`。
11. 重复、越序和冲突对账请求：同一 `reconcileRequestId` + 同一结论摘要幂等；摘要冲突或越序关闭性结论由 B′ 按本地前置条件拒绝，永久冲突进入 `sync_conflict`，不得无限重试。
12. 同步期间不得再次执行原任务，也不得提交与已提交结论冲突的状态变更。
13. 强制终止持锁进程后，新进程可以恢复存储与唯一写入者锁；回收残留套接字时不得偷走存活实例的锁。写入中断后的存储恢复不得只覆盖正常 close 后再打开。

每项证据须包含：双方节点身份、代码 SHA、监听与认证方式、可复现命令、完整输出、存储与日志位置。当前状态：**跨机验收未跑**。同机进程内或同盒双进程测试不能作为本清单的通过证据。真实双机验收不得把执行接口裸露到公网。变更单见 `docs/exec-protocol/v1-two-node-change-ticket.md`（本轮只编制与审核，不实施宿主变更）。
