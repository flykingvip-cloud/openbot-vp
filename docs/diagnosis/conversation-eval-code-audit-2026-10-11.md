## 模型结论：Job 还是 schedule

现有诊断调度是每租户一个 JSON 记录，不是可并发、可暂停、可失败重跑的 Job。自进化 cron 才是 job，而且必须经过 confirm，当前 confirm 常量关闭。

M0 采用被动事件日志，不新增 Diagnosis Job，也不往 `diagnosis-schedules/` 写评价。schedule 继续只服务已有 `diagnose()` tick。

## M0 可落地最小事件集

下列事件都已有相近生产者，或只需在现有 `emitChatInboundStage` / lifecycle 上补字段。正确性一律允许缺省。

1. `chat.user_persisted` 与 `chat.dispatch_started`  
   已有。键：`runId`（= `chat.send` 的 idempotency key）、`sessionKey` 的哈希、网关受理时刻。补：服务端 membership 的 `tenantId`。不写消息正文。

2. lifecycle `phase=start` / `phase=end` / `phase=error`  
   已有。键：`runId`。补：`attempt`（从 1 递增的整数；今天没有发出）、`errorClass`（沿用 timeout/error 或 failover reason 的枚举，不写原始错误串）、`endedAt`。`correctness` 省略即 `unassessed`。

3. `chat.model_started`、`chat.first_token`、`chat.model_finished`、`chat.assistant_persisted`  
   嵌入式非心跳路径已有。效率字段只用已出现的 `modelTtftMs`、`modelMs`。不引入 `llmTtftMs`。CLI 与心跳标成缺失，不要估。

4. `chat.context_compiled`  
   仅当上下文编译器开启。字段：`compileMs`、`runId`。编译器关闭则该事件缺失。

5. 子 Agent 关联  
   在子 run 的 lifecycle 上补 `parentRunId`（或 requester session 的哈希）。开始/结束仍用子 `runId` 自己的 lifecycle。不新造一套 subagent 事件。

6. 协作轮次
