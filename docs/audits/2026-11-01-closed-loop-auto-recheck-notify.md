# 自动处理、原场景复验与大白通知

这份文档只定范围。本回合不实现自动处理、复验执行器或通知发送。当前已落地的只有：显式否定写入 TaskOutcome correction，诊断按指定版本只读 tip，以及企业诊断页上由用户填入的任务对照。

依据仍是隔离合同：`docs/audits/2026-11-01-closed-loop-isolation-contract.md`。下面凡是和那份合同冲突的做法，都按合同失败关闭。

## 触发：什么时候可以自动，什么时候必须人工

人工，而且已经有入口的：

- 用户在任务卡上点击「结果不符合要求」。请求必须带服务端给出的 `taskId`、`agentId`、`outcomeVersion`。调用者是已认证的 `platformUserId`，并且与任务 `subjectRef` 一致；企业任务还要 membership 租户一致。
- 企业诊断页只有用户填齐任务、数字人和结果版本，才把这三元组放进 `diagnosis.diagnose`。留空不得改去读最近一条任务。

仍然禁止自动的：

- 自由文本里的引用、转述、泛泛否定、新要求，以及没绑定任务的「上次不对」。这些只澄清，不写 TaskOutcome。
- 「应该是 / 请改为 / 目标是」仍只改已绑定的 workspace 目标，不写 TaskOutcome，也不触发复验或通知。
- 工具失败、诊断零发现、inject 被接受。这些都不是「用户否定了结果」，也不能当成复验通过。

以后若要做自动处理，触发只能是已经成功落盘的 correction 事件（`task.corrected`，且 `revisionKind=correction`），不能是聊天句子，也不能是诊断报告本身。自动处理默认关闭。没有单独的产品开关被明确打开之前，代码路径必须直接返回未执行。

## correction 和原场景复验

correction 已经存在，语义不变：

- 对一条已关闭的 tip 追加一个新版本，重算门闩，保留历史。
- 不是 reopen，不是新的一次执行，界面也不能写成「已重新执行」。
- 预期版本和 tip 不一致时返回 `version_conflict`。后一次不得覆盖先一次。
- 学习贡献的撤销只跟这条 correction 走，并且必须用隔离的 stores。生产默认不传 stores 时仍走原来的 `loadConfig()`。

原场景复验是另一笔，现在没有：

- 输入是 correction 之后的那一个版本，加上当时的任务合同和原始场景标识（会话、输入摘要或已保存的场景引用）。没有这些标识就失败关闭，不拿「最近一次成功会话」代替。
- 复验自己成功或失败，都再追加版本，或写一条只挂在该 `outcomeVersion` 上的复验观察。不得改写被否定的旧版本，不得把旧版本的 `taskJudgement` 改成成功。
- 复验执行器失败、超时、工具失败，记为这次复验未完成。tip 保持 correction 后的失败判定。工具失败仍然只是观察。
- 没有复验记录时，诊断详情继续显示「未复验」。不得因为诊断跑过、或通知发出去了，就把这一行改成已复验。

版本顺序：

1. 关闭时的 tip，版本 N。
2. 用户否定成功，版本 N+1，`revisionKind=correction`。
3. 以后的复验若发生，版本 N+2，或一条指向 N+1 的复验观察。诊断要读哪一版，仍由调用方显式传入。

## 大白通知

通道仍然是现有的会话注入，不新开通知队列，不复用 pending-delivery，也不复用 TaskOutcome outbox。那两处的重试语义是原通道投递和任务事件，不是「告诉用户结果被否定了」。

身份：

- 收件人必须来自已核对的 platform user。`subjectRef` 今天不是 `platformUserId`，中间没有映射。
- 映射不存在、为空、或和任务主体对不上：不发送。失败关闭。
- 禁止退回 `agent:main:main`，禁止退回 `diagnosis:canary:daibai`，禁止沿用 cron 在 owner 缺失时退回主会话的逻辑。

最小内容只陈述已经发生的事实：

- 任务 id、被否定的结果版本、correction 后的版本和判定。
- 一句「这是纠正记录，不是重新执行」。
- 不写负责人猜测，不写复验已通过，不写用户已读。

去重和节流：

- 同一 `taskId + outcomeVersion + 收件人` 只发一次。重复的 correction 回放（同一 commandId）不得再发。
- 发送失败留在通知自己的事实里，不把原任务打回 `awaiting_delivery`，也不把 tip 改回成功。
- inject 返回 `delivered: true` / `conversation_accepted` 只表示转写被网关接受。诊断页现有「报告已投送到指定大白对话区」仍是这层意思，不能当成用户读过，也不能当成任务成功。

## 和现有 tip、拒绝、诊断的边界

| 已有能力                    | 本方案允许它做的                             | 不允许它顺手做的                   |
| --------------------------- | -------------------------------------------- | ---------------------------------- |
| TaskOutcome tip             | 权威判定。诊断和通知只读它                   | 被通知结果或诊断零发现改写         |
| `task.outcome.rejectResult` | 主体对指定版本追加 correction                | 自动再跑原场景，或发出大白消息     |
| `diagnosis.diagnose`        | 按调用方给出的版本返回 `taskOutcomeEvidence` | 选择最近任务，创建处理单，发送通知 |
| 企业诊断选择器              | 用户手填任务、数字人、版本                   | 用卡片 id 或最近 tip 填空          |

跨用户、跨租户继续由现有 subject 和 membership 租户拒绝。选择器多填的字符串不是授权。

## 建议拆开的后续 PR

1. 复验记录只读模型。验收：没有记录时诊断仍显示「未复验」；写入一条失败观察后，指定版本能读到「复验未完成」，旧版本判定不变。不做执行器。
2. 原场景复验执行器，默认关闭。验收：开关关闭时调用返回未执行且不追加版本；开关打开且场景标识缺失时失败关闭；合法运行只追加新版本。不做通知。
3. 大白通知。验收：主体映射缺失时不发送且不改任务；同一版本重复消费只送一次；inject 接受不会把任务标成已读或成功。不做复验。

三笔都不要和治理执行门（remediation、Issue 复查回写、claimContract、治理自动执行）绑在一起。

## 明确不做

- 本回合不实现自动处理、复验执行器、通知发送。
- 不新建第二套诊断库、处理状态机或通知队列。
- 不猜测 `subjectRef` 对应的人，不批量回填历史任务归属。
- 不把终端用户加成 `operator.write` 或 `operator.admin`。
- 不把「已重新执行」「已复验」「用户已读」写进没有对应证据的界面。

## 安全、租户和主体

- 否定和以后的复验写入，都要求已认证 `platformUserId` 与 `subjectRef` 相同。企业范围还要求服务端租户等于 `scope.tenantId`。
- 客户端传入的 subject 字符串、邮箱形式的 `client.user`、卡片 id，都不是授权。
- 历史任务如果创建时没有 platformUserId，`subjectRef` 可能是会话键。以后的通知和复验同样失败关闭，不补写。
- 诊断选择器只决定读哪一个版本。读的时候仍走诊断现有的调用者校验；对不上就 `unauthorized`，并且不返回对方的判定正文。
